<interfaces>
The verdict function reads these existing `Scorecard` fields (from data/measure/types.ts). All four
timing stages are nullable (a run may skip the performance pass) and `heap` is nullable (may skip the
memory pass):
- Scorecard.engine: TimingStat | null   (medianMs, p95Ms, samples[])
- Scorecard.genTxn: TimingStat | null
- Scorecard.bridgeCall: TimingStat | null
- Scorecard.render: TimingStat | null
- Scorecard.heap: HeapAttribution | null  (totalHeapDelta, cubeStoreRecords, gridStoreRecords, viewResultRows, agGridInternals, unit, method)
- Scorecard.rowCounts: {leaf, aggregate, gridRows}
End-to-end update->render latency (BASE-03) = sum of the four stage medianMs (null-coalesced to 0).

BASE-04 target families (all four REQUIRED - none optional):
- PER-SCORECARD (lower-is-better, one run at a time via evaluateScorecard): update->render latency,
  engine p95 CPU, per-tab heap ceiling (reference + small-heap machines).
- ENVELOPE-LEVEL (higher-is-better, once per ladder via evaluateEnvelope): max records x fields the
  client sustains within the comfortable tier; max sustained batch size x rate without breaching the
  jank wall. These are boundary facts derived from the WHOLE ladder (savedRuns / envelope-stats), not
  from any single Scorecard, so they are NOT rendered as per-scorecard badges.
</interfaces>
