<objective>
Build the out-of-process, server-side test-data API in Toolbox's Grails (Hoist Core) layer that the
harness drives. It generates seeded, deterministic datasets parameterized by shape (HARN-01) and emits
update batches parameterized by pattern/breadth/throughput over both HTTP and WebSocket push (HARN-02).

Purpose: Locked decision - synthetic data generation MUST NOT run in the measured browser JS thread
(it would compete for the main thread and pollute results). It lives server-side, built into Toolbox's
Grails layer specifically so the effort also yields reusable server-side Hoist patterns. This plan is
independent of the client measurement core (different language, different repo path), so it runs in
parallel with 02-01.
Output: A new `datalab` namespace in Toolbox's Grails app: a generator service, a WebSocket push
service, and an HTTP controller, plus URL mappings.
</objective>

  <name>Task 1: Seeded, shape-parameterized dataset generator service (HARN-01)</name>
  <files>../toolbox/grails-app/services/io/xh/toolbox/datalab/DataLabService.groovy</files>
  <action>
Create `DataLabService.groovy` in a NEW `datalab` package/namespace (distinct from `portfolio` so
harness load never perturbs the existing portfolio demo - per RESEARCH Open Question 4). Model it on
the existing `PortfolioService` randomized-generation pattern, but generalize generation to be driven
by request parameters rather than the fixed portfolio shape.

Implement a method like `List<Map> generateSnapshot(Map shapeParams)` where shapeParams carries the
HARN-01 knobs that mirror the client `DatasetShapeConfig`:
- `leafRowCount` - number of leaf rows to emit.
- `fieldCount` + `fieldTypeMix` - generate that many fields with the requested type distribution across
  number / string / date / object-valued fields. Object-valued fields are required (Phase-1 heap
  question) - emit a small nested map for those fields.
- `dimensions` - emit categorical dimension fields with bounded cardinality so the client Cube produces
  a realistic aggregate-row count (few/coarse dimensions over many leaves = large-leaf-plus-aggregate).
- `seed` - seed a deterministic RNG (`new Random(seed)`) so the SAME seed + params regenerate byte-identical
  data. This is the reproducibility decision - the generator must be a pure function of (seed, params).

Each generated leaf row is a `Map` with a stable unique `id` (so the client can apply diffs by id).
Keep it a plain Grails service. Do NOT couple to the portfolio domain objects. Add a class-level comment
noting this is reusable server-side harness infrastructure (HARN-06 byproduct), not throwaway.
  </action>
  <verify>Grails compiles (`../toolbox` build / `grailsw compile` if available, otherwise confirm syntax matches existing services); calling generateSnapshot with a fixed seed twice yields identical output (assert in a quick scratch test or document the determinism guarantee in the SUMMARY).</verify>
  <done>DataLabService generates seeded leaf rows whose count, field count, field-type mix (incl. object-valued), and dimension cardinality are all driven by request params; identical (seed, params) yields identical data.</done>
</task>

Create `DataLabPushService.groovy` modeled on `PositionService.pushUpdates`'s WebSocket timer pattern.
Inject Hoist Core's `webSocketService` and `DataLabService`.

Implement a controllable push loop that, given a scenario's update knobs (pattern, breadth, batchSize,
ratePerSec, durationSec, seed), generates successive deterministic update batches via `DataLabService`
and pushes each batch to a dedicated harness channel/topic (distinct channel from the portfolio demo)
via `webSocketService` (study the exact `pushToAllChannels`/`pushToChannel` API used by
PositionService). Provide start/stop control methods so the client harness can begin a stream for an
iteration and stop it cleanly between iterations.

Honor the four update patterns from the client `UpdatePattern` knob:
- `steadyTrickle` - small batches at a steady rate.
- `periodicBurst` - large batches at intervals.
- `broadReplace` - emit a full re-snapshot signal (drives client Cube.loadDataAsync, not updateDataAsync).
- `targetedNarrow` - small batches touching `breadth` fields on few records.

This service is the WS-push half of HARN-02; only the delivery mechanism differs from the HTTP diff -
both carry the same batch shape so the client resolves them to the same two-op ingest contract.
