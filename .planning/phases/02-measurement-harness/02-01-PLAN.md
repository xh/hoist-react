<task type="auto">
  <name>Task 1: Define the harness config + result type schema (the knob taxonomy)</name>
  <files>data/measure/types.ts</files>
  <action>
Create `data/measure/types.ts` defining the full serializable type schema for the measurement core.
Follow Hoist conventions: named exports only, `null` over `undefined`, no em dashes in comments, file
header copyright block matching `data/index.ts`.

Define these interfaces/types (all plain serializable JSON - no class instances, so they round-trip
through ViewManager JsonBlob storage):

DATASET-SHAPE KNOBS (HARN-01) - `DatasetShapeConfig`:
- `leafRowCount: number` - leaf records loaded to the Cube's internal store.
- `dimensions: string[]` - Cube grouping dimensions (drives the aggregate-row count via dimension
  cross-product cardinality; comment: large-leaf-plus-aggregate = many leaves under few/coarse dims).
- `fieldCount: number` and `fieldTypeMix: FieldTypeMix` - number and type distribution of fields.
  Define `FieldTypeMix` as weights/percentages across `'number' | 'string' | 'date' | 'object'`
  (object-valued fields probe the Phase-1 heap question). Comment the object-valued intent.
- `aggregators: string[]` - which aggregated fields the View computes (affects ViewResult size and
  dataOnlyUpdate fast-path eligibility).
- `seed: number` - RNG seed for deterministic generation (reproducibility decision).

UPDATE KNOBS (HARN-02) - `UpdateConfig`:
- `pattern: UpdatePattern` where `UpdatePattern = 'steadyTrickle' | 'periodicBurst' | 'broadReplace' | 'targetedNarrow'`.
  Comment each: determines snapshot vs diff and fullUpdate vs dataOnlyUpdate.
- `breadth: number` - fields changed per updated record (narrow vs wide).
- `batchSize: number` and `ratePerSec: number` - throughput knobs.
- `transport: Transport` where `Transport = 'http' | 'webSocket'`. Comment: only the delivery adapter
  changes; both resolve to the invariant two-op ingest contract (Cube.loadDataAsync / updateDataAsync).
- `durationSec: number` - how long the update stream runs for a measured iteration.

PROTOCOL KNOBS (HARN-05) - `ProtocolConfig`:
- `warmupIterations: number`, `measuredIterations: number`, `gcSettleMs: number`. Provide a documented
  default sane set as an exported `const DEFAULT_PROTOCOL: ProtocolConfig` (e.g. warmup 5, measured 20,
  settle 50ms) - note these are Claude's-discretion defaults, persisted with each run.

TOP-LEVEL `ScenarioConfig`:
- `name: string`, `dataset: DatasetShapeConfig`, `update: UpdateConfig`, `protocol: ProtocolConfig`,
  `notes?: string`.

OUTPUT TYPES (HARN-04 / HARN-05):
- `TimingStat` = `{ medianMs: number; p95Ms: number; samples: number[] }`.
- `HeapAttribution` = `{ cubeStoreRecords: number; gridStoreRecords: number; viewResultRows: number;
  agGridInternals: number; totalHeapDelta: number; unit: 'bytes'; method: HeapMethod }` where
  `HeapMethod = 'performanceMemory' | 'measureUserAgentSpecificMemory'`. Comment: agGridInternals is the
  opaque remainder (total delta minus owned layers); never read from AG Grid source.
- `Scorecard` = `{ compute: TimingStat; bridgeCall: TimingStat; render: TimingStat; heap: HeapAttribution;
  rowCounts: { leaf: number; aggregate: number; gridRows: number }; transactionsPerBurst?: number }`.
  Comment the compute-vs-bridge meaning: compute = Hoist-side JS (genTransaction) timed directly;
  bridge = the opaque cost of crossing into AG Grid (applyTransaction) timed directly + deferred render.
- `EnvMetadata` = `{ userAgent: string; crossOriginIsolated: boolean; exposeGc: boolean;
  preciseMemory: boolean; heapMethod: HeapMethod; capturedAt: string }`.
- `RunResult` = `{ scenario: ScenarioConfig; scorecard: Scorecard; env: EnvMetadata; adapterId: string;
  overheadMs: number }`. Comment overheadMs: the null-scenario instrumentation overhead (HARN-03
  "bounded, documented overhead").

Reference 02-RESEARCH.md "Pattern 1: The knob taxonomy" and "Full scorecard per run" for the exact knob
set. Do NOT invent extra knobs beyond what HARN-01/HARN-02/HARN-05 require - data-composition-as-config
(field-by-field null %, etc.) is explicitly deferred per CONTEXT.

Create `data/measure/CandidateAdapter.ts` defining the swap seam that lets the harness measure baseline
and candidate implementations apples-to-apples through one protocol (HARN-06; Claude's-discretion -
"lean toward a common-interface/swap approach if it fits the real contracts").

Ground the interface in the real Phase-1 contracts BEFORE writing it: use `hoist-get-members Cube` /
`hoist-get-members View` to confirm the actual `loadDataAsync(rawData, info)` / `updateDataAsync(...)`
signatures and the `View.result` shape. The interface must mirror the invariant `View.result -> Store`
seam (Phase-1 names this as the integration seam later phases prototype behind), not an idealized
abstraction.

Define `interface CandidateAdapter` with at minimum:
- `readonly id: string` - identifies which implementation produced a RunResult (e.g. 'baseline-cube').
- `loadSnapshotAsync(rawRows: PlainObject[]): Promise<void>` - full snapshot ingest (maps to
  Cube.loadDataAsync for the baseline).
- `applyDiffAsync(diff: PlainObject[]): Promise<void>` - incremental diff ingest (maps to
  Cube.updateDataAsync for the baseline).
- `getResultRowCount(): number` - current result row count (for heap accounting + scorecard rowCounts).
- `getResultRows(): unknown[]` - current materialized result rows (for view-result heap accounting).
- `disposeAsync(): Promise<void>` - teardown between scenarios.

Add a JSDoc block at the top explaining: the baseline adapter wraps Cube/View/Store/GridModel; a
candidate adapter (Phase 6/7) implements the same interface over a different engine; the harness
instruments and measures against the interface so the implementation behind it is the only variable.
Do NOT implement a concrete BaselineAdapter here - that belongs with the orchestrator plan (02-05),
which has the live Cube/View/GridModel wiring. Import `PlainObject` from `@xh/hoist/core` (or the
correct Hoist path - confirm via `hoist-search-symbols PlainObject`).

Edit `data/index.ts` to add `export * from './measure';` in the appropriate export block (after the
