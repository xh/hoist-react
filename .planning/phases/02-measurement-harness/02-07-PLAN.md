Close gaps 1 and 2 from 02-VERIFICATION.md - the two "input" corrections that make the harness
measure the right work against the right shape.

Gap 1 (headline correctness, HARN-03/HARN-05): today `runIterationAsync` only times
`measureGridSync` (Boundary 5 - the grid add/update/remove diff). The actual engine work -
`adapter.applyDiffAsync` -> `Cube.updateDataAsync` + the connected View re-aggregation that
produces new aggregate rows (Boundaries 1-4) - runs on the line BEFORE timing starts and is never
measured. Source confirms this pipeline is fully awaitable: `Cube.updateDataAsync` does
`await forEachAsync(this._connectedViews, v => v.noteCubeUpdated(changeLog))`, and `noteCubeUpdated`
synchronously runs `generateRows()` -> `loadStores()` -> `updateResults()` (the `View.result`
@observable.ref write) within that await. So wrapping the awaited `applyDiffAsync` in
`performance.now()` brackets captures the real Boundaries-1-4 cost. `BoundaryInstrumentation`
already ships an unused `measureBoundary()` for exactly this; wire it.

Gap 2 (realistic shape, HARN-01): `BaselineAdapter.buildPipeline` creates a FLAT GridModel (no
treeMode) and a View query with `includeLeaves: isEmpty(dimensions)` - which is FALSE whenever
dimensions are configured, so with 3 dimensions only the top aggregate level surfaces (5000 leaves
collapse to ~9 flat rows, no children, no leaves). That is a degenerate aggregate, not the
large-leaf-plus-aggregate tree HARN-01 requires. Fix: treeMode GridModel + tree column + a View
with `includeLeaves: true` so leaves sit under the deepest aggregate nodes, and row-count accessors
that reflect the full hierarchy (these counts also feed heap attribution in 02-08).

Purpose: make pipeline compute the primary measured number and run it against a realistic tree.
Output: corrected `BoundaryInstrumentation.ts`, `MeasurementHarness.ts`, `BaselineAdapter.ts`,
`types.ts`, verified live in flagged Chrome.
