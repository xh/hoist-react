<task type="auto">
  <name>Task 2: MeasurementHarness orchestrator -> RunResult (HARN-05, HARN-06)</name>
  <files>data/measure/MeasurementHarness.ts, data/measure/index.ts</files>
  <action>
Create `MeasurementHarness.ts` defining the orchestrator that produces a complete `RunResult` (the 02-01
type). It extends a Hoist base so `runner()` is available (confirm HoistBase via hoist tools).

DATA-SOURCE BOUNDARY (read first - this is the integration seam 02-06 wires to): The harness is
transport- and endpoint-agnostic. It lives in hoist-react and has ZERO knowledge of the Toolbox
`datalab/snapshot` or `datalab/diff` endpoints. It NEVER fetches data. Instead:
- the caller (Toolbox `DataLabModel.runAsync()` in 02-06) PRE-FETCHES the initial snapshot rows and
  PRE-LOADS them into the adapter via `adapter.loadSnapshotAsync(rows)` BEFORE handing the adapter to the
  harness, AND
- the caller supplies an injected per-iteration data-provider callback
  `nextBatchAsync: () => Promise<PlainObject[]>` that returns the next pre-fetched diff batch on demand.
The harness, inside the protocol loop, calls `nextBatchAsync()` to obtain a batch and then applies it via
`adapter.applyDiffAsync(batch)`. This keeps the split architecture clean (core stays endpoint-agnostic,
Toolbox owns the fetch over HTTP or WebSocket) and is consistent with the 02-04 calibration callback
contract (`loadNRowsAsync`/`clearAsync`), which the caller also supplies pre-fetched rows for.

Implement `runScenarioAsync(args: {scenario: ScenarioConfig; adapter: CandidateAdapter; nextBatchAsync: () => Promise<PlainObject[]>; loadNRowsAsync: (n: number) => Promise<void>; clearAsync: () => Promise<void>}): Promise<RunResult>`
(keep the signature tight; `scenario` + `adapter` are the conceptual inputs, the two callbacks are the
injected data source so the harness stays endpoint-free):
1. Capture `EnvMetadata` up front via a `captureEnvMetadata()` helper: `navigator.userAgent`,
   `self.crossOriginIsolated`, `exposeGc = typeof window.gc === 'function'`, a `preciseMemory` heuristic,
   `heapMethod = detectHeapMethod()` (from 02-04), `capturedAt = new Date().toISOString()`. (RESEARCH
   "Detecting environment for run metadata".)
2. Assume the initial snapshot has ALREADY been pre-loaded into the adapter by the caller (the harness
   does NOT fetch or load the snapshot itself - it only verifies via `adapter.getResultRowCount() > 0` and
   throws a clear error if the adapter is empty, so a mis-wired caller fails loudly). Calibrate per-record
   bytes via `calibratePerRecordBytesAsync` (02-04) using the injected `loadNRowsAsync`/`clearAsync`
   callbacks (the caller supplies pre-fetched rows behind these), including an object-valued-field
   calibration variant.
3. Run the protocol via `runProtocolAsync` (02-05 Task 1):
   - setupAsync: confirm snapshot is loaded (pre-loaded by caller), grid mounted + warmed (Pitfall 6).
   - runIterationAsync: obtain the next diff batch via the injected `nextBatchAsync()`, apply it through
     `adapter.applyDiffAsync(batch)`, then `measureGridSync` (02-03) to get {computeMs, bridgeCallMs,
     renderMs}; after the iteration, forceGcAndSettle + `attributeHeap` (02-04) for the heap sample.
     Collect per-iteration {compute, bridge, render, heap}.
   - betweenIterationsAsync: `forceGcAndSettleAsync(protocol.gcSettleMs)`.
4. Reduce samples into a `Scorecard`: `compute`/`bridgeCall`/`render` as `TimingStat` (median + p95 via
   toTimingStat); `heap` as the final steady-state `HeapAttribution`; `rowCounts` from the adapter;
   optionally `transactionsPerBurst` (RESEARCH Open Question 3 - measure dataReaction/genTransaction
   invocations per burst if reachable).
5. Measure instrumentation overhead via `measureOverhead` (02-03) and put it in `RunResult.overheadMs`
   (HARN-03 bounded/documented overhead).
6. Return `RunResult { scenario, scorecard, env, adapterId: adapter.id, overheadMs }`.

The orchestrator must NOT itself generate OR fetch data (out-of-process, caller-owned only) and must NOT
hardcode the baseline - it takes any `CandidateAdapter` plus the injected data-provider callbacks, which
is exactly what makes it reusable for candidate evaluation (HARN-06).

Add `export * from './MeasurementProtocol'; export * from './BaselineAdapter'; export * from './MeasurementHarness';`
to `data/measure/index.ts`.
