a concrete `BaselineAdapter` that implements `CandidateAdapter` over the real Cube/View/Store/GridModel
pipeline, and the `MeasurementHarness` orchestrator that takes a `ScenarioConfig` + an adapter and
returns a complete `RunResult`. This is where instrumentation (02-03), heap attribution (02-04), and the
config/result types (02-01) come together into the durable, reusable engine.

engine to be reusable for BOTH baseline and candidate evaluation - the adapter seam + one protocol make
that real. This is the load-bearing assembly plan; it is two tasks because the orchestration logic is
non-trivial and integrates three prior modules.
Output: `MeasurementProtocol.ts`, `BaselineAdapter.ts`, `MeasurementHarness.ts`, all exported.

  <files>data/measure/MeasurementProtocol.ts, data/measure/BaselineAdapter.ts</files>
  <action>
PROTOCOL - create `MeasurementProtocol.ts`:
Implement `runProtocolAsync<S>(args: {protocol: ProtocolConfig; setupAsync: () => Promise<void>; runIterationAsync: () => Promise<S>; betweenIterationsAsync: () => Promise<void>}): Promise<S[]>`:
- call setupAsync once.
- run `protocol.warmupIterations` warmup iterations and DISCARD their samples (JIT warmup, lazy alloc,
  cache fill - cite Pitfall 6: ensure grid is mounted/warmed so we don't measure a remount full-replace).
- run `protocol.measuredIterations` measured iterations, calling `betweenIterationsAsync()` (forced GC +
  settle) before each, collecting each iteration's sample.
- return the array of measured samples.
Also implement pure stats helpers `median(xs: number[]): number` and `p95(xs: number[]): number` (sort +
index; no library - RESEARCH says compute directly) and `toTimingStat(samples: number[]): TimingStat`
producing the 02-01 `TimingStat`. Comment WARMUP/MEASURED defaults are Claude's discretion (use
DEFAULT_PROTOCOL) but must be persisted with the run.

BASELINE ADAPTER - create `BaselineAdapter.ts`:
Implement `class BaselineAdapter implements CandidateAdapter`. It owns the live baseline pipeline: a Cube
(+ View, + the View's Store / a GridModel). Confirm the real wiring via `hoist-get-members Cube/View/GridModel`.
- `id = 'baseline-cube'`.
- `loadSnapshotAsync(rows)` -> `cube.loadDataAsync(rows)` (the invariant snapshot op).
- `applyDiffAsync(diff)` -> `cube.updateDataAsync(diff)` (the invariant diff op).
- `getResultRowCount()` / `getResultRows()` -> from `view.result` (use the confirmed ViewResult shape).
- Expose accessors the harness needs for measureGridSync + heap accounting: a way to get the live
  `genTransaction`/`applyTransaction` callables (or the GridModel's agApi) for Boundary 5, and the
  cube-record / grid-record / view-row counts for heap attribution. If genTransaction is not directly
  reachable from outside GridModel, document the closest reachable seam in the SUMMARY and measure the
  applyTransaction half via agApi (the bridge cost is the priority).
- `disposeAsync()` -> tear down / clear the cube and grid between scenarios (`@managed` children;
  XH.safeDestroy pattern - confirm via hoist tools).
Use Hoist conventions: extend the right base (HoistModel/HoistBase as appropriate), `@managed` for child
models, named exports, Async suffix.

<task type="auto">
  <name>Task 2: MeasurementHarness orchestrator -> RunResult (HARN-05, HARN-06)</name>
  <files>data/measure/MeasurementHarness.ts, data/measure/index.ts</files>
  <action>
Create `MeasurementHarness.ts` defining the orchestrator that produces a complete `RunResult` (the 02-01
type). It extends a Hoist base so `runner()` is available (confirm HoistBase via hoist tools).

Implement `runScenarioAsync(scenario: ScenarioConfig, adapter: CandidateAdapter): Promise<RunResult>`:
1. Capture `EnvMetadata` up front via a `captureEnvMetadata()` helper: `navigator.userAgent`,
   `self.crossOriginIsolated`, `exposeGc = typeof window.gc === 'function'`, a `preciseMemory` heuristic,
   `heapMethod = detectHeapMethod()` (from 02-04), `capturedAt = new Date().toISOString()`. (RESEARCH
   "Detecting environment for run metadata".)
2. Drive the data substrate via the adapter: load the initial snapshot (rows generated out-of-process by
   the 02-02 Grails API - the harness fetches them; in-browser generation is forbidden). Calibrate
   per-record bytes via `calibratePerRecordBytesAsync` (02-04) using adapter load/clear, including an
   object-valued-field calibration variant.
3. Run the protocol via `runProtocolAsync` (02-05 Task 1):
   - setupAsync: snapshot loaded, grid mounted + warmed (Pitfall 6).
   - runIterationAsync: apply one update batch through the adapter, then `measureGridSync` (02-03) to get
     {computeMs, bridgeCallMs, renderMs}; after the iteration, forceGcAndSettle + `attributeHeap` (02-04)
     for the heap sample. Collect per-iteration {compute, bridge, render, heap}.
   - betweenIterationsAsync: `forceGcAndSettleAsync(protocol.gcSettleMs)`.
4. Reduce samples into a `Scorecard`: `compute`/`bridgeCall`/`render` as `TimingStat` (median + p95 via
   toTimingStat); `heap` as the final steady-state `HeapAttribution`; `rowCounts` from the adapter;
   optionally `transactionsPerBurst` (RESEARCH Open Question 3 - measure dataReaction/genTransaction
   invocations per burst if reachable).
5. Measure instrumentation overhead via `measureOverhead` (02-03) and put it in `RunResult.overheadMs`
   (HARN-03 bounded/documented overhead).
6. Return `RunResult { scenario, scorecard, env, adapterId: adapter.id, overheadMs }`.

The orchestrator must NOT itself generate data (out-of-process only) and must NOT hardcode the baseline -
it takes any `CandidateAdapter`, which is exactly what makes it reusable for candidate evaluation (HARN-06).

Add `export * from './MeasurementProtocol'; export * from './BaselineAdapter'; export * from './MeasurementHarness';`
to `data/measure/index.ts`.
