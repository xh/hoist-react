Hoist Chart V2 - decision brief, 15 Nov 2026

Stay on Highcharts. Build a Hoist chart spec on top of it.

Most Hoist charts are time series. Highcharts Stock was the deepest library we tested, our clients already license it, and a Hoist-owned JSON spec makes every chart persistable, user-editable and writable by an agent.

  1. Time series: develop, do not switch.A TimeSeriesChartModel on Highcharts Stock, GridModel-grade: typed spec, series and axis objects, store binding, persistence.
  2. Everything else: same library.Five purpose-built family models, in order. Today's raw ChartModel stays as the escape hatch. No second chart library in Hoist.
  3. One JSON contract for people and agents.Spec plus state, validated by Hoist, drives the chart, the settings panel, dashboards, saved reports and agent tools.

One library covers the rest. Highcharts is first-class on every family we need often.

Architecture

Own the spec, not the renderer.

A family of purpose-built chart models sharing one JSON contract, rendered by Highcharts behind an internal seam. One library means pluggable backends would be needless generality; the seam keeps a future swap affordable.

Proposed API

Config extends Spec, the GridModel way. Every change is a method.

Developers pass one flat config. Its spec keys are the definition: what agents edit and widgets save. User tweaks go to a state overlay keyed by id. Code may pass functions or named refs. JSON uses refs only.

// In code: flat config, like GridModel
new TimeSeriesChartModel({
  store, persistWith,        // infra keys
  onPointClick: e => ...,    // functions OK
  // spec keys - the definition
  timeField: 'date',
  rebase: 'percent',
  range: 'ytd',
  showNavigator: true,
  panes: [{id: 'main'}, {id: 'dd', size: 0.35}],
  axes: [{id: 'perf',
          format: {id: 'percent', args: {precision: 1}}}],
  series: [
    {id: 'fund', field: 'FUND'},
    {id: 'peers', field: 'nav', splitBy: 'symbol'},
    {id: 'dd', of: 'fund', transform: 'drawdown',
     pane: 'dd', type: 'area'}
  ]
});
// Definition methods - author edits
model.addSeries(spec)
model.updateSeries('dd', {pane: 'main'})
model.removeSeries('peers')
model.setSpec(spec)       // replace
model.updateSpec(patch)   // merge patch
model.getSpec()           // as authored

// State methods - user tweaks
model.hideSeries('spx')
model.updateSeriesState([{id: 'fund',
                          type: 'area'}])
model.setRange('mtd')
model.restoreDefaultsAsync() // clears state

// UI, code and agent tools share
// this one list. Each writes one layer.
// Saved in a DashCanvas widget,
// through the existing Dash persistence
{
  viewSpecId: 'timeSeriesChart',
  layout: {x: 0, y: 0, w: 8, h: 6},
  state: {
    v: 1,
    source: {id: 'navs'},
    chart: {
      spec: {timeField: 'date', ...},
      series: [{id: 'spx', hidden: true}],
      range: 'ytd'
    }
  }
}

// Type and source live on the widget,
// not in the spec. Other families follow
// the same rules later.

Control surface - live

One config model, two drivers.

Form controls and agent tool calls change the same spec through the same actions and the same validator. Try the agent buttons, including the bad call. Switch the renderer to see the spec is library-neutral.

Agents and generative UI

Agents name the data. Hoist checks it.

A chart references a source and its fields; it never carries made-up numbers. Hoist validates against the source's typed fields and answers with the valid choices, so one retry is usually enough. The same schema serves chat, dashboards and saved reports.

Plugs into hoist-chat-kit as it is

  • Registers as a ChatUiComponentSpec (show_time_series_chart) over the real model, so the expanded view gets the settings panel free.
  • Schema in chat-kit's subset: no $ref, bounded arrays, props in priority order. One object argument for OpenUI, not 13 positional ones.
  • Closes gaps the handoff notes list: no dashboard placement, edits never reach the agent, made-up trends, no panes or bands.
  • No formatter functions and no raw Highcharts options in the agent schema. Model text is escaped.

Read: chat-kit branch genui-building-blocks (most current) and five related branches.

Roadmap

Time series ships first and ships deep. Breadth follows, one family at a time.

Nothing breaks: today's ChartModel stays as the escape hatch. The Highcharts 13 upgrade goes in a Hoist major before V2 code depends on it. Durations are guesses for one or two developers working with agents.

Phase 1 exit test

The spike's NAV and drawdown charts built with the real model in Toolbox, persisted to local storage, restored after reload.

Phase 2 exit test

A Toolbox dashboard of chart and grid widgets, edited from the settings panel, saved and restored through ViewManager.

Phase 3 exit test

An agent builds a two-chart, one-grid report from a prompt. The user edits and shares it. The agent then describes the edited state correctly.

Recommendation and decisions

Develop on Highcharts. Same library for breadth. Decide four things now.

1. Time series: develop the pair on Highcharts Stock

Build TimeSeriesChartModel on a Hoist-owned spec. Do not switch, do not add a complement.

Strongest argument against: we deepen dependence on one commercial vendor whose types we cannot ship and whose 13.x broke options. ECharts was a clear second.

Confidence high. The spec keeps a later move to ECharts affordable: about 150 more lines of Hoist time-series code.

2. Everything else: Highcharts, in this order

First-class: Category, Heatmap, Distribution, Scatter, Flow. Treemap aligned. Thin path: raw ChartModel for network, org, gauge, radar. Extension point, not a Hoist family: 3D surface, process flow.

Strongest argument against: breadth of catalogue is not quality, and one vendor for everything concentrates risk. Answer: the spike found Highcharts' breadth quality at least equal to ECharts', and the spec keeps a move affordable.

Confidence high on one library, medium on the order (depends on real report widget mix).

Decide now

  1. Adopt the spec-first chart family on Highcharts (option e).
  2. Upgrade Hoist to Highcharts 13 in the next major, with the validated palette.
  3. Agree the data source contract with the first app that builds reports.
  4. Build the portable groundwork (named refs, registries) in core with Chart V2, so Grid can follow (findings/14).
